## 0. Bottom line

- **The 26c file is fully mappable.** Its bundle was made by the same esbuild (0.28.x, same helper code) with the same settings as
  build 15's. Because `main.js` does `await import('./avodah/index.js')`, esbuild wraps almost every module in its lazy-ESM helper
  (`jn(()=>{…})` in 26c, `Tn` in 15), and each wrapper closes exactly one module — so the 26c bundle cuts itself into modules with
  exact boundaries (179 segments); the unwrapped tail (main.js and its static imports) is cut by aligning unit hashes with build 15's.
- **Of build 15's 225 bundled src files, 200 are unchanged in 26c, 25 changed, none gone.** The other 2 src files
  (`src/avodah/works/index.js`, `indexb.js`) have no importer and are in neither bundle. three.js r186 and its addons, the 21 bundled
  content JSON files, the vendored matter.js and the kohen GLB are all unchanged.
- **12 modules of 26c have no build-15 source** — the code of builds 16–26c: `focus17`, `fx18`, `ramp19`, `kiyor20`, `deshen21`,
  `maaracha22`, `pis23`, `pen25`, `heichal26` (all `src/avodah/shift/`, names confirmed by the build reports and by their CSS
  prefixes), two small ones whose file names did not survive (an event log `"mk.evlog"` and a gait table taken out of hero35.js),
  and one 4-byte piece of esbuild glue.
- **Volume to recover:** ≈ 62k normalized tokens of new code inside the 25 changed modules (two thirds of it in `day33.js`, which grew
  ×3.9) + ≈ 55k tokens in the 11 new modules (145 KB minified, 5,682 prettified lines). Roughly 3,800 lines in the repo's dense style.
- **Verification is objective and node-only:** a recovered module is right when its minified units normalize to the same hashes as
  26c's (proved on `temple.js` below); the final target is a byte-identical `out/index.html` (same esbuild, same three, same page shell).
- **Lost for good (not in the bundle):** every comment of builds 16–26c, the tests added after build 15 (144: 568 → 712), the
  autoplayer `tools/autoplay35.js` + `tools/autoplay35-run.cjs`, and PROJECT.md's entries for builds 16–24 (25–26c survive as
  reports in the session transcript).

## 3. How the map was made (and why it can be trusted)

1. `build-marked.mjs` rebuilds build 15 with build.mjs's exact settings three ways: plain (byte-identical to `dist/app.js` — checked),
   with a no-op `__R1M("path")`/`__R1E("path")` call at each module's top/end (labels), and with `minifyIdentifiers: false` (the same
   units with their source names; its wrappers even carry the paths).
2. `units.mjs` cuts each bundle into units (top-level statements; one per `var` declarator and per comma element; a wrapper's body
   statements are units too) and **normalizes** them: every local name → `_`, `{k:a}` ≡ `{k}`; strings, numbers, property names, keys
   and punctuation kept. Build 15: 8,495 units / 167 segments; 26c: 8,877 / 179.
3. `modmap.py` labels build 15's units (marked build, aligned to the plain one), cuts 26c into modules (wrappers + the aligned tail),
   aligns the two module sequences by DP on shared unit hashes and stable tokens, then pairs leftovers order-free (that caught
   `game/audio.js`, which moved into the lazy graph when 26c's `avodah/sound.js` began to import it, and `walk.js`, now imported earlier).
   A module is **unchanged** when its multiset of normalized units equals 26c's.
4. `moddiff.py` measures each change as a token diff (units paired order-free); `annotate.mjs` writes banner comments at every module
   start and prettifies both bundles → `recovery/work/p26c.pretty.js` (195,984 lines, sha256 e2bcf083…) and `p15.pretty.js`
   (184,289 lines, sha256 e38638b9…) + `*.ranges.json`; the line ranges below are in these files.
5. `symmap.py` names 26c's minified top-level symbols from build 15's source names: **5,034 of the 5,107 (98.6 %)** distinct
   top-level names declared in the old modules get their source name; the new modules' references to old modules resolve to source names at ≈ 85 %
   (a regex count; a scope-aware count is part of R2). → `recovery/work/symmap26c.json`.
6. **Proof of the verification loop** (scratch copy, not the repo): build 15's `temple.js` + the two hunks the diff shows
   (`M.pyre22 = { ...M.cedar }` and the great pyre's logs drawn with `'pyre22'`) → rebuilt → its units equal 26c's temple.js units
   exactly (0 units only in the port; the 5 "only in 26c" are the module's `init_x()` calls that the marked build files under the
   previous module).

Which builds touched what (from build-number suffixes in the new literals): `day33.js` b17–b26 (b26 most), `focus17` b17 (+16–26 hooks),
`audio.js` b17–b26, `avodah/sound.js` b17–b26 (26c), `shift/index.js` b17–b26 (one `__SH<n>_OFF` switch per build), `stations.js` b17–18,

## 7. Risks

1. **Byte parity may stop short** of identical bytes (esbuild's renamer counts every symbol of the bundle; a construct that minifies to
   a different but equivalent form). Fallback: alpha-equivalent parity per unit, which still proves the same program up to names.
2. **Plain `_`-normalized equality is blind to swapped locals** (two variables traded in one expression hash the same) — hence the
   alpha-renamed check in R2 and the byte check in R8; do not sign off a module on the R1 metric alone.
